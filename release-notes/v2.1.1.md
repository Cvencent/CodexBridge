# CodexBridge v2.1.1

这个版本修复 v2.1.0 之后在真实 CBDP 联调中暴露的若干结果编码问题。全部问题都
是 Bridge 侧缺陷，手机端和 ESP 端不需要为这些改动调整代码。

## 修复

- **`thread.read` 丢失全部消息**：`thread.read` 的返回里同时含有
  `pending_approvals`，旧的编码器按响应字段“猜”对象类型，先命中审批列表，
  于是把消息对象整体丢掉。现在按命令方法分派对象编码，`thread.read` 会同时
  返回 thread、message 和 approval 对象。
- **超长字段会让整条命令失败并断开连接**：一个超过 64 KB 的标题会让
  `threads.list` 整体无法编码，客户端表现为会话被静默拆掉。现在所有对象文本
  按会话协商的 `max_frame_bytes` 做有界裁剪，并按预算打包对象，超长字段不再
  影响其他字段。
- **`thread_ref` 恒为 0**：Companion HTTP 通道的 CBDP 会话没有接引用注册表，
  所有 `thread_ref` 都是 0，客户端无法用紧凑引用定位线程。现在 Companion
  通道与设备 TCP 通道共用同一个引用注册表。
- **紧凑引用不能回传上游**：`thread_ref` 之外的选择器现在会还原成上游需要的
  `thread_id`，`thread.read` 等命令可以用 ref 直接调用。
- **`projects.list` 直接抛异常**：引用注册表不认识 `project` 类型，
  `projects.list` 一编码就抛 `ValueError`。现在注册表支持 `project`，并且
  未知引用类型降级为 0，不再让异常逃出会话线程。

## 验证

- 完整单元测试：`678` 项全部通过。
- 真实安装版 WebSocket 端到端联调：
  `threads.list` 首页 40 个 thread 对象，携带可回传 `next_cursor`；回传游标后
  第二页 22 个对象；`thread.read` 返回 67 个对象（thread + message）；
  `models.list` 31 个对象；`projects.list` 12 个对象；全程无异常断连。
