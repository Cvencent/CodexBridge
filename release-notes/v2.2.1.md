# CodexBridge v2.2.1

这个版本修复 CodexBridge 与桌面 Codex 抢同一线程写入权的问题。此前在电脑端
Codex 里点发送或点引导时，会先弹一次错误，但消息有时仍然发出去了。

## 根因

桌面 Codex 会对每个已打开的会话持有线程写入锁。Bridge 把“写入锁已存在”一律
当作桌面留下的陈旧文件，直接改掉锁文件来接管该会话。Windows 允许在锁仍被
持有的时候重命名该文件，所以 Bridge 确实把桌面正在使用的会话抢了过来。

结果是两边各自用自己的 app-server 写同一个会话：桌面下一次发送或引导就会
报写入冲突，而 Bridge 那边已经把内容写进去了。这正是“先报错、有时其实发出去
了”的来源；排队后再加引导之所以更容易复现，是因为它连续触发两次写入。

## 修复

- **不再抢占活锁。** 清理锁之前先尝试独占打开探测：锁仍被活动进程持有时保持
  原样，写入改走桌面归属通道，不再由 Bridge 的第二个 app-server 抢写。
- **陈旧锁仍会回收。** 真正因为崩溃残留的锁文件（没有任何进程持有）照旧清理，
  避免桌面异常退出后会话永久卡住。

## 影响

- 在电脑端 Codex 里发送消息、排队和引导不再先弹写入冲突错误。
- 手机或设备回复桌面已打开的会话时，仍按桌面归属路由，不会产生分叉会话。
- 既有的配对、CBDP 无线配对、订阅、命令和附件行为不变。

## 验证

- 独占持有锁文件时，清理函数返回未清理且文件保留；释放后才可回收。
- 桌面正在运行的会话不再被 Bridge 抢占写入权。
- 全量单元测试 909 项通过（新增 3 项针对锁探测的回归测试）。
