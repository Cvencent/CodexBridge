# CodexBridge v2.2.14

这个版本修复两台 ESP 首页「运行中」数量与实际不符、长期停在 0 或旧值上的问题。

## 问题现象

- 两个 ESP 的 `running_count` 显示 0，而 Codex 里确实有任务在跑。
- 另一些时候数值会卡在一个偏高的旧值上（例如推送一直停在 4，实际只剩 3），
  且对应事件的时间戳数分钟不更新。

## 根因

**一、采集线程会静默死亡**

`/api/admin/codex-status` 显示 `collector_state=idle`、`last_snapshot_epoch=0`，
即进程启动后一次都没有采集过。用 py-spy 检查进程栈确认：home-counter、
discovery、poll_speech 线程都在，唯独 `run_codex_collector` 已消失。

原因是采集循环只捕获 `(AppServerError, OSError, ValueError)`，而
`hub.publish()` 会写事件库，`sqlite3.DatabaseError` 既不是 `OSError` 也不是
`ValueError`，一旦抛出就会穿透整个循环让线程结束，且没有任何地方记录。

**二、计数仍由消息库推导**

采集器在某个 turn 结束后不再重发它的 `task` / `status` 记录，残留记录继续被
统计；而 `system.codex_state(0x0704)` 只在数值变化时才追加，于是一个错误的
高值就被永久留在设备上。

## 修复

- **采集线程不再静默退出**：改为捕获所有异常，上报 `error` 状态并进入有界
  退避重试。
- **计数改用采集快照作为权威来源**：新增
  `running_turns_from_snapshot()`，按快照里 `working` / `waiting_user` /
  `queued` / `starting` 的 turn 生成运行集合；Hub 通过 `note_live_turns()`
  接收，`counts()` 以它为准。
- **每次采集后重新评估聚合计数**：数值未变时仍不会追加重复事件，不增加射频
  流量。
- **按 turn 键（`thread_id`, `turn_id`）匹配终态结果**：同一会话之后开启的新
  轮次仍会正常计为运行中。

## 影响

- 设备首页的运行中数量与 Codex 实际状态保持一致，任务结束会及时回落。
- 协议字段、TLV tag、事件结构与端口均未改变，设备端无需改动。

## 验证

- 全量单元测试 **944 项通过**。
- 新增 5 项针对性测试，均验证过「还原缺陷后测试失败」：
  已结束轮次不计入、同线程新轮次重新计入、聚合列表中的已结束轮次被排除、
  采集线程遇 sqlite 异常仍存活、权威集合覆盖陈旧记录。
- 本机实测：修复前推送值卡在 4 而实际为 3，事件时间戳近 200 秒不更新；
  修复后连续采样 **9/9 次一致，0 次不一致**，并观察到计数变化时事件重新推送。
